## 2. Fault A — engine: a bar can be evaluated from the snapshot taken while it was forming

`backend/app/live.py` (build at HEAD; no `backend/app` diff between
`origin/main` and this branch):

- `poll()` L343-347 refreshes bars ONLY when `time.time() >= self.bars[-1].ts + BAR_SECONDS`.
- `refresh_bars()` L187-203 fetches from `bars[-1].ts − 4h` and MERGES everything
  fetched into `self.bars` by timestamp — including the still-forming bar
  (`fetch_4h_bars` L19-21: "Includes the still-forming bar — callers must
  filter on closed-ness"). Only closed bars are persisted (L199-203).
- So at the 04:00:0x boundary the in-memory window gains a 04:00Z bar
  holding only its first seconds (Bitstamp open 84,121.29 — one cent ABOVE
  the 84,121.28 limit). From then until 08:00 no refresh runs (`bars[-1]` is
  that forming bar, its end is 4h away).
- At 08:00:0x `poll()` calls `refresh_bars()` then `catch_up()`. If the ONE
  Bitstamp fetch at that instant fails (`fetch_4h_bars` returns `[]` on any
  exception, L43-45; `refresh_bars` then returns having changed nothing,
  L192-193) — or returns the 04:00Z candle before Bitstamp has finalized
  it — `catch_up()` L205-241 sees the stale forming snapshot, now with
  `bar.ts + 4h <= now`, and processes it as the closed bar: low ≥ limit →
  pending cancelled, S3 flat.
- The next poll's refresh succeeds, overwrites the 04:00Z bar with its final
  values and persists it (which is why the stored row is correct today),
  but `catch_up` skips it: `bar.ts <= last_processed` (L210).
- No `degraded` event is expected on this path: `poll()` refreshes
  `last_data_ok` from the ticker every poll (L304-306), and the OHLC fetch
  failing once does not change it.

The module docstring (L9-11) states the invariant the code does not keep:
"a 4h bar is processed once wall-clock passes its end boundary AND it has
been fetched from REST; late REST data therefore delays processing rather
than producing a signal on an incomplete bar." A forming bar fetched at its
open satisfies "fetched from REST" and later passes the boundary without a
re-fetch.

What a log line would add: whether 08:00:0x saw "Bitstamp OHLC fetch
failed" (the failed-fetch branch) or nothing (the not-yet-final candle
branch). The fix below closes both.

Fix A (engine, `live.py` + `config.py`):
1. record the wall-clock time each bar was last fetched (`_bar_fetched_at`);
2. a bar is FINAL only if it was fetched at or after `bar.ts + BAR_SECONDS + bar_final_grace_s`
   (new setting, default 30 s, for Bitstamp's own candle finalization);
3. `catch_up` processes bars in order and STOPS at the first non-final one,
   logging `bar_not_final` (rate-limited) — late data delays processing, as
   the docstring promised;
4. `poll` refreshes whenever a closed bar is still unprocessed, so a failed
   fetch retries every `poll_seconds` instead of once per 4 hours;
5. bars loaded from the DB at boot are final by construction (persisted only
   when closed, from a post-close fetch).

Cost: signals and exits publish up to `bar_final_grace_s` + one poll later
than today (≤ 90 s on a 4h bar). The executor's stale guard is 3 bars.

## 3. Fault B — executor: a transient order-status read booked a residue nothing could settle

`app/mirror.py` `_close_leg`, single-leg / same-side path (L4598-4640):

- after `place_market` it reads `order_status(cloid)` ONCE and, on
  `FILLED`/`CANCELLED` with `0 < filled_qty < qty`, books the difference as
  a residue (`close_partial`, "retrying next poll") — N9e, 2026-09-16.
- nothing retries. The single-leg path never sets `close_cloid`, so
  `_settle_close` (L4271, which re-reads the venue and attributes from the
  POSITION read) never runs for it; the residue is pure belief.
- the next polls compare venue net (0.03134) with the ledger sum (residue +
  0.03134) → `diverged`; the trend leg's stop reads OPEN → `in_flight` →
  grace twice (`netting_inconsistent` 1/3, 2/3, L4230-4245) → third poll →
  `LEDGER_DIVERGENCE` → flatten everything.

Which read produced `0 < filled < 0.93614` on an order the venue records as
fully filled in the same second is the one detail only the log answers:
`hl.order_status` L636-640 derives `filled = origSz − sz` from the venue's
order record, and a transitional record (status already terminal, `sz` not
yet 0 while the 4 prints land) is the shape that fits. The fix does not
depend on which it was: a residue must come from the venue's POSITION, never
from one order-status read.

Fix B (executor, `mirror.py`): the single-leg close uses the same
belief-before-send + settle-from-position machinery the opposed-book path
already has (`close_cloid` / `close_qty` / `close_net_before` persisted
before `place_market`; `_settle_close` immediately and on every later poll;
"one close in flight at a time"). A transient read becomes a one-poll grace;
a genuine partial IOC keeps exactly the residue the venue shows; the netting
second look treats the open close ref as in-flight, so the mismatch counter
cannot run while the close is unsettled.

Two small additions that fell out of the gate tests:
- `_check_drift` no longer pages `position_drift` while a close or
  re-establish ref is in flight: the ledger is belief-before-send by design
  in that window, the state is already announced (`close_unconfirmed` /
  `reest_unsettled`) and bounded by the netting second look.
- the close cloid carries a per-send counter (`P-<ts>-<n>-X`): two closes on
  one leg inside the same second (a settle, then a retry) must never share
  an id. The `-X` suffix every reader keys on is unchanged.

## 4. What the fix does NOT change

- The engine's fill rule (`bar.low < limit`, strict) and the executor's
  doctrine that an engine-unacknowledged fill is closed (`orphan_fill`). If
  the engine and the venue still disagree on a bar (a Bitstamp low exactly
  at the limit vs an HL print at it), the cost is one round trip, not a halt.
- The ~4h `unbooked_fill_unprotected` window on a pullback maker fill.
- Nothing on the carry sleeve.
